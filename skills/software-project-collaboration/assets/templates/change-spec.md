# CHANGE-ID：用一句话写用户可感知的结果

状态：draft / ready / implementing / verified / released / blocked
优先级：MUST / SHOULD / COULD / DEFER
工程风险：R0 / R1 / R2 / R3（或项目既有等级与映射）
基线、所有者、更新时间、适用环境：

## 1. 问题与依据

谁在什么场景遇到什么问题；目前如何做；真实复现或材料来源。区分事实、假设、建议。

## 2. 范围和已有约束

做什么、不做什么；复用哪些已有能力；当前用户授权与项目限制在哪里。
跨仓库列每个仓库、基线、接口负责人；不复制未知上游实现。

## 3. 用户路径和契约

输入→操作→输出→再次进入。规定 API、权限、状态、错误、文件与历史、并发、取消和重试。
0/false/空字符串/空数组/null/缺省要分别定义。迁移、兼容和回退按实际需要补充。

## 4. 验收

| AC | 条件与动作 | 预期可观察结果 | 层级/环境 | 对应风险 |
| --- | --- | --- | --- | --- |
| AC-01 | 待填写 | 待填写 | 待填写 | 待填写 |

每项写可判定行为，不能只写“稳定、友好、完善”。需求变化同步此表，不事后改低标准。

## 5. 实现与验证范围

最小纵向切片、相关路径、必要依赖、目标命令；记录估算区间和依据，不冒充实测。
不把所有技术细节塞进 spec；复杂决策引用 ADR。

## 6. 未决项

问题、影响、现有默认值、谁能决定。已明确的常规实现不重复向用户求确认。
