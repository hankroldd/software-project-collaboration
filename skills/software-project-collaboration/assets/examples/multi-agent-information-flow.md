# 合成示例：三个开发宿主共享同一项目事实

此例说明记录与消息怎样配合，不代表已运行 Claude Code、Codex 或 OpenCode，也不提供可执行的宿主消息 API。角色名称只是示例，按实际可用工具替换。

## 起点

一个虚构的目录应用将列表接口统一为 `{ "items": [] }`；空列表放在 items 内，不返回裸数组。已有 OpenSpec 变更目录、任务表和 PR 流程，本次直接沿用。需求和契约 revision 4 已由项目负责人确认，当前代码尚有按 revision 3 解析的消费者。

| 参与者 | 任务与身份 | 允许写入 | 共享责任 |
| --- | --- | --- | --- |
| 协调者，Claude Code | 变更 C-LIST 的集成人 | 现有任务表、集成分支、必要状态摘要 | 维护主记录、决定结果纳入、共同验证 |
| API 执行者，Codex | T-API / attempt-1 | 自己工作树的服务端与对应测试 | 提交接口行为和证据，不改 UI 或公共状态 |
| UI 执行者，OpenCode | T-UI / attempt-2 | 自己工作树的解析与空态 | 读取 revision 4，交回消费者变化与证据 |

UI 的 attempt-1 曾使用 revision 3；协调者已核实原写入停止并保存其未提交成果，才分配 attempt-2。公共测试环境由集成人串行使用；两个工作树不据此获得同时改共享数据的权利。

## 主记录入口

- 项目入口指向已有 `openspec/changes/list-envelope/`，其中规格、任务与契约各有一个主位置。
- 该变更的现有任务表记录 task、attempt、BASE、契约、写入范围、候选和原问题；revision 初始为 8，由协调者维护。
- `docs/STATUS.md` 只摘要为“列表契约联动实现中”，引用变更目录；不复制另一份任务状态表。
- 每个 worker 的验证记录与候选一起交回 PR/受控产物；示例中的候选名称 A、U、I 是占位，实际工作填写提交或未提交内容身份。

## 消息与记录的推进

| 事件 | 消息中的关键信息 | 主记录与执行动作 |
| --- | --- | --- |
| 协调者通知新契约 | C-17，change，发 T-API/attempt-1 与 T-UI/attempt-2；revision 4 链接；需确认受影响范围 | 任务表 revision 9 标明两任务依据的契约与待确认状态 |
| API 接收 | reply_to C-17；已读 revision 4；将修改返回结构和空集合验证 | API 继续限定范围；不因通知而扩大写入路径 |
| UI 尚未确认 | 消息工具显示发送成功，接收者未给实际回应 | 仍记待确认；不推断已采用，不重复派发第三个 UI 尝试 |
| UI 接收并提出缺口 | reply_to C-17；可读契约，但无法访问示例证据 | 协调者提供有权访问的脱敏夹具；排版等无关工作可继续 |
| UI 确认行动 | reply_to C-17；读取 revision 4；列解析与空态变化、所需验证 | 协调者在原任务记录确认，依赖恢复；不复制整份契约 |
| 旧结果迟到 | T-UI/attempt-1 返回候选 U-old，revision 3，mock 检查通过 | 标为旧尝试待比对；不覆盖 attempt-2，不把旧绿灯记为 revision 4 已验 |
| API 交回 | R-API-1，result，候选 A、实际后端检查及未验 UI 范围 | 协调者先回复收到，再读差异与证据；done 暂不改变整体验收结论 |
| 重复交回 | R-API-1 再次到达 | 引用原处理记录；不再应用同一提交或重跑副作用 |
| UI 交回 | R-UI-2，result，候选 U、解析及真实页面观察，缺少共同后端联测 | 协调者记录候选与具体未验项，安排共同候选验证 |
| 状态更新发生冲突 | API 的总结建议仍依据任务表 revision 8，当前已为 10 | 协调者比较建议中的事实，合并仍有效项；保留新契约确认与旧结果标记，不用旧摘要覆盖整表 |
| 集成与验收 | 集成候选 I，标明纳入 A、U、冲突解决和实际组合验证 | 按实际结果采纳或拒收，保留原问题；再更新 STATUS 摘要。未部署仍记未部署 |

“收到 R-API-1”“采用候选 A”“共同候选 I 验证通过”是三项不同事实。只有实际完成对应动作时才记录；失败或环境不可达时明确保留未验范围。

## 中途换协调者

原协调者交接现有任务表 revision 10、各任务/尝试、未采纳结果、原问题、共享环境占用和消息 C-17 的确认情况。新协调者先核当前提交、活跃进程与原任务，接替公共记录维护责任；没有理由重新派发已在执行的 API/UI 任务。

新协调者发现 U-old 与当前任务无关时可保留其可复用改动建议，但必须在新契约和候选上重新判断。原消息、候选与处置仍可追溯；新会话不会将旧拒收自动清零。

## 需要保存的最终信息

保留有效规格/契约、实际纳入候选、共同验证、未闭合项、部署状态与下一步责任。任务表保留必要的尝试与处置历史，STATUS 保持简短。无需提交完整聊天、全部工具输出或各宿主的运行时缓存。
