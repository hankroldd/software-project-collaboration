# 多人、多代理与跨宿主协作

本模块组织协作，不增加新的任务平台或审批层。单人小改可用一段任务说明；出现并行写入、多个 harness、跨机器或接管时，再读 [协作协议](collaboration-protocol.md)。

需要代理间持续交互、跨会话共享上下文或维护项目事实时，读 [消息与项目共享信息](agent-communication-and-project-memory.md)。使用现有消息通道与项目记录；消息确认、结果接受、代码集成分别记录。

## 输入与责任

读取原目标、有效项目规则、规格、已有审查问题、当前 STATUS 和实际授权。
确认参与者是人、当前会话的子代理，还是另一台机器/另一个开发工具的独立进程。
模型品牌、工具名称、会话名字均不代替责任人、实际工作目录和权限。
一个需要共同验收或集成的变更组指定一位协调者/集成人；不同独立变更可以有各自负责人。
沿用项目维护者与发布负责人的权限，不让代理协调角色覆盖他们。
协调者负责范围、共享契约、依赖与最终结论；实施者交付限定范围；审查者独立核实。
这些角色可以由人或代理担任；负责协调不自动获得合并、部署或他人资源的权限。
已有授权持续有效。任务卡和其他代理的转述用于定位授权，不能自行扩大权限。

## 选择合适的并行方式

| 场景 | 默认安排 | 必须核对 |
| --- | --- | --- |
| 独立研究或只读审查 | 按问题并行，结果由协调者汇总 | 同一候选、原始材料、报告各自存放 |
| 同一工作树的多位写入者 | 默认串行；仅在明确的互不重叠文件范围内并行 | Git索引/分支操作、生成器、格式化、锁文件和共享数据的唯一写入者 |
| 不同工作树或独立clone | 按任务分支并行，完成后集中集成 | 真实cwd/HEAD、共享refs/config、端口、数据库、卷与产物 |
| 不同机器或不同harness | 使用已有Issue/PR/任务卡传递版本化结果 | 本地消息/任务状态不自动互通；共享环境的写入与发布排队 |
| 同一API/schema/迁移尚未定案 | 先确定契约与所有者，再并行消费者 | 兼容性、变更顺序和对旧任务的影响 |

有独立工作且能节省时间才并行；紧耦合、小改动或资源不足时直接串行。
不强制所有实施任务串行，也不为了并行把共享逻辑拆成多个症状补丁。
任务范围互不重叠仅是起点，运行资源和组合行为也要检查。
使用宿主原生派发、权限、工作树或现有团队工具；不要手工改宿主运行时状态文件。
本套只有被选为本次流程主持者时才统筹；作为worker时按任务卡执行，不另开总计划或验收账本。
项目已有选定编排器时，本套作为专项参考。多个框架被同时点名时分配职责，按 [流程职责与冲突处理](workflow-governance.md) 执行。
文字约定不会关闭另一个harness已启用的hooks；只在授权范围内核对实际配置，不假装所有工具共享同一开关。

## 派发任务

每项任务使用 [任务卡](../assets/templates/task-card.md)，已有等价记录时补字段而不复制一份。

1. 固定交付目标、MUST与验收，链接原始材料和共享契约。
2. 指定任务ID、执行者和集成人；会重派或跨会话时再加本次尝试ID。
3. 记录仓库、分支/工作树、BASE；检查现有未提交成果，不能覆盖。
4. 分配允许修改的路径、共享资源、产物位置和依赖，明确谁管理Git索引与集成。
5. 说明实际工具权限、可用环境、模型/预算限制，以及能否启动进一步子任务。
6. 指定交回的结果与证据、接收方、回复位置和影响本任务的主记录版本，避免只有口头“已完成”。

只传完成该任务所需的上下文。实现者需要契约与必要历史，独立审查者需要原始需求、差异和原问题。
不把预期审查结论或“不要报某问题”的暗示交给审查者；也不遗漏影响实现的用户纠正。
跨宿主不假定共享父会话、技能版本、模型设置、待办列表或审批状态。
只有确有收益且不重复工作时再嵌套派发；总并发和费用遵守既有约束，不静默切模型。

## 执行期协调

协调者维护已有任务系统或 [集成记录](../assets/templates/integration-ledger.md)；通常一个变更组一份即可。
实施者分别写自己的结果，协调者更新公共状态，避免所有人同时改STATUS。
双方可直接讨论接口与证据；改变已确认契约、资源分配或范围的结论，交由对应维护者更新主记录并通知受影响任务。讨论线程不能成为另一份有效合同。

| 实施者报告 | 协调者动作 |
| --- | --- |
| `done` | 收取候选与证据，进入集成判断；不直接记为整体验收通过 |
| `done-with-concerns` | 核实剩余问题及影响，不隐藏未完成MUST |
| `needs-context` | 先从现有材料补齐，只有必要产品决定才询问用户 |
| `blocked` | 区分权限、环境、契约冲突和真实技术失败，继续无阻塞工作 |
| `cancelled` | 核实进程/写入/外部副作用状态，保留可恢复成果 |

等待时处理其他独立工作，不高频空轮询，也不在每个任务后询问是否继续。
用户新消息传给受影响执行者，更新具体范围或契约版本；未取消的目标继续保留。
发现共享文件、端口、数据库或环境争用时，暂停相应写入，划清资源或收回并行范围。
没有消息或任务过期只能说明需要核实，不能据此认定旧执行者已经停止。
接管前保留未提交成果、实际进程与副作用状态；旧尝试的迟到结果先核身份，不能自动合并。
具体接管、取消和资源分配见 [协作协议](collaboration-protocol.md)。

## 集成与审查

### 固定交回对象

每项结果提供实际BASE、候选HEAD，或明确标记未提交的补丁与内容指纹。
HEAD相同而工作区不同的成果不可视为同一候选；未跟踪文件也需要纳入交付范围。
时间窗口审查保留提交列表和窗口定义，不用HEAD~1代替整项任务起点。
跨仓按各自SHA和父仓引用一起核对；不能只报告子仓已完成。
结果记录技能/契约的相关版本、执行目录、真实依赖与验证证据，秘密只保留受控引用。

### 在共同候选上判断

1. 核对任务、尝试、执行者、范围与文件；迟到或已替代结果先单列，再决定是否采用。
2. 读取实际差异与调用方，检查接口、状态、生成文件、依赖和迁移是否相容。
3. 按项目Git策略集成，保护用户改动；不擅自force push、重置或改写他人历史。
4. 形成明确的集成候选并验证受影响组合路径；各分支分别通过不代表组合通过。
5. 合并后有相关内容变化，判断哪些证据失效并补相应验证；不用旧审查批准新增行为。
6. 代码、程序验证、业务接受和目标环境发布分别记状态。

独立审查可以由合适的人或代理承担；项目要求的人员审批仍按实际身份执行。
不能把同一实现者的另一会话自动算作独立审查，也不因模型不同就提高证据等级。
每条发现给位置、触发条件、影响与依据，允许零发现；修复后保留原问题ID并追加复核。
不要求无理由重跑同一检查；环境、输入、代码或判断有实际疑点时再补证据。
有限修复预算用于重新定位或报告阻塞，不能把未解决的S0/S1或本期MUST改记为完成。

## 接续与清理

采用 [接续说明](../assets/templates/handoff.md)，把恢复工作所需的事实留在项目既有位置。
STATUS保持短：当前目标、候选/环境、已完成证据、未闭合问题、下一步和最近核实时间。
详情链接到spec、决策、任务、审查和证据；不复制整个聊天、工具输出或隐藏思维过程。
交接保留尚未确认的关键消息、尚未接受的结果、主记录版本及维护责任；摘要被读取不代表旧会话已经交出写入责任。
接手者先核git/运行状态和原问题，不能只依赖宿主的记忆、任务done标记或“继续”提示词。
停任务、卸载技能、结束会话和撤销已发生的外部副作用是不同动作，按实际状态处理。
只有确认结果已接收、必要证据已保存、所属进程已停止后，才清理本任务资源。
不删除他人的未提交改动、工作树、容器、数据库或卷；未知归属先保留并说明。

## 完成与停止条件

R0/R1通常不需独立协作记录；R2/R3按实际风险保留集成与验收证据。
完成报告说明交付结果、实际验证、未验范围与重要遗留项，不堆代理流水。
任务身份、共享契约或候选无法对应时，先恢复对应关系，再给完成结论。
权限不足时完成可审查部分，指出具体受阻步骤；已有授权和信息足够时直接推进。
