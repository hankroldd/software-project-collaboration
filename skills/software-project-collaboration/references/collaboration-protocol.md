# 多人、多 agent、多 harness 协作协议

仅在多个写入者、跨会话接管、跨工具或跨机器时读取。这里的harness指运行代理的宿主，如Codex、Claude Code、OpenCode；相同技能名称不保证相同版本、权限或上下文。

代理消息、接收确认、项目事实索引和信息更新规则另见 [消息与项目共享信息](agent-communication-and-project-memory.md)。本文件负责写入、资源、接管与集成，避免维护两套状态流程。

## 1. 最少共享什么

沿用Issue/PR、现有任务系统或变更目录中的记录。一个需要共同集成的变更组确定协调者，工作者只维护自己的产物；团队不必新增全局控制服务。

| 记录 | 至少包含 | 为什么需要 |
| --- | --- | --- |
| 任务 | task_id、目标/AC、当前约束、依赖、责任人/集成人 | 明确谁在做什么，避免两个主持者重复派发 |
| 执行尝试 | 重派时的attempt_id、实际执行者/宿主、开始或最近核实时间 | 区分重试、旧会话和迟到结果 |
| 代码与契约 | 仓库、BASE、分支、工作树、契约版本、候选或补丁指纹 | 避免测A交B、前后端依据不同版本 |
| 资源 | 允许写入路径、运行目录、端口/服务、数据与产物范围 | 文件隔离之后仍能发现运行时争用 |
| 结果 | 实际修改、检查与证据、未闭合问题、当前副作用、下一步 | 可接续而不必重新获得全部聊天 |

普通任务不必填完整表。没有重派就不新造尝试编号；不用为每次读文件记心跳。
约定检查时间用于发现失联，不自动赋予接管权。Markdown任务卡是协作记录，不是锁或权限控制器。
跨机器需要并发领取时，复用已有系统的原子领取/版本更新机制；没有此能力就由协调者串行分配。

## 2. 三类隔离要分别确认

### 工作内容

- 同一可变文件、Git索引、分支或迁移序列在同一时段有明确写入者。
- 同一工作树默认串行写入；经协调的互不重叠文件可并行，但Git操作、全库格式化、生成器和锁文件由指定人负责。
- 不在共享索引中各自运行git add -A/commit；这可能把别人的成果并入自己的提交。
- 不为绕过冲突强制在多个工作树检出同一分支，不在另一个工作树替他人切分支或改历史。
- Git worktree分离工作目录、HEAD与索引，但部分refs和默认仓库配置仍共享。
- git worktree lock保护工作树管理信息免于清理/移动/删除，不阻止其他进程改文件。
- 对submodule、特殊Git布局或宿主隔离能力先确认实际支持；必要时使用独立clone。
- 工作树不是凭据或操作系统隔离。要运行不可信代码时，使用项目批准的执行隔离和权限。

上述Git边界来自[官方worktree文档](https://git-scm.com/docs/git-worktree)。不要把目录名字当成实际隔离证明。

### 运行资源

| 资源 | 分配方法 | 常见遗漏 |
| --- | --- | --- |
| 端口与进程 | 记录服务、端口、启动者、进程身份与运行目录 | 另一个任务启动成功，却连到旧服务 |
| 数据库/队列/缓存 | 使用隔离数据库、schema、前缀或独占测试时段 | 用共享库做清表/迁移，影响别人验证 |
| Compose/容器/卷 | 区分项目名与本任务持久化数据，核对显式名称和外部资源 | project name不同但固定宿主端口、外部卷或同一数据库仍冲突 |
| 构建与临时文件 | 独立输出目录/缓存键，必要生成步骤串行 | 两个构建器覆盖同一dist或生成客户端 |
| 测试账号与业务对象 | 使用可识别的合成数据范围，清理仅限本任务 | 一个测试删掉另一个测试的数据 |
| 模型与GPU | 沿用已有队列或约定容量，记录并发与预算 | 并行任务争抢显存，误判为代码或性能回归 |
| 共享部署环境 | 通过既有发布负责人和队列串行改变同一目标 | 不同分支先后覆盖同一环境却共用旧验收 |

[Compose project name](https://docs.docker.com/compose/how-tos/project-name/)可用于环境区分，但仍需核对显式资源与对外依赖。不要为此默认新增容器、锁服务或任务调度平台。

### 权限与配置

- 在实际宿主检查cwd、可读写范围、工具、网络、子代理和发布权限，不能只看提示词里写着“只读”。
- 沿用当前用户授权；代理转发的“用户已经同意”需要能对应有效来源，不自动升级权限。
- 不为修复宿主间差异开启bypass、关闭sandbox或复制另一工具的全局允许清单。
- 技能、hooks、MCP、agent配置分别核版本与来源；安装技能不应自动授予执行/发布权限。
- 不复制个人凭据、.env或运行时会话缓存；交接只记变量名和经授权的取得方式。
- 参与者读同一项目合同；宿主专属配置留在适配层，不把另一宿主的字段当可执行保护。

## 3. 开始、变更、接管与取消

### 正常开始

1. 协调者核对依赖和现有活跃任务，确定资源、基线和单个交付目标。
2. 工作者读取任务卡、有效项目规则与相关契约，报告实际工作目录和工具限制。
3. 范围冲突先由协调者解决；不因等待一个问题而停掉其余已授权工作。
4. 进展写事实：完成了什么、还缺什么、候选和证据在哪里。idle或消息已送达不代表工作已完成。

### 契约发生变化

API/schema/权限语义/迁移顺序由指定负责人更新主契约，说明兼容影响并通知相关参与者。
旧任务记录自己依据的版本；共享契约改变后，协调者判断继续、调整或取消哪些任务。
需要重做的部分补验证，已有效的独立成果保留。不要让两边各自猜一套“兼容实现”。
修改技能或工作规程版本也按同样方式处理：不要在活跃任务中让不同工具悄悄读取不同版本。

### 失联或需要接管

1. 先查询宿主任务/会话状态、工作树和已知进程，保存未提交内容及已发生副作用。
2. 能恢复原执行者且仍适用时优先接续，不直接重复执行写入、发布或迁移。
3. 确需换执行者，由协调者记录接管原因、当前候选、原问题、接收者和新的attempt_id。
4. 对共享写入，先确认原执行者已停或已失去写入能力。无法确认时使用另一个隔离工作区并暂停争用资源；不同时放两个执行者写原资源。
5. 原尝试之后返回的结果先标为旧结果，对比范围/候选和当前契约后再决定是否保留或择取。

协调者换人也按接续处理：保留已派任务、未决集成与发布状态，说明谁现在负责公共记录和集成；不能因新会话开始就让两位协调者各自重新派发或发布。
不因心跳超时就自动抢占。仅写一个owner字段或改名不能防止旧进程继续写入；需要硬互斥时使用已有执行系统的能力。
不无差别kill进程、删锁文件、删除工作树或重建共享数据库来“解除阻塞”。

### 用户取消、变更方向或停止代理

记录最后已知状态，停止本任务新副作用，并按宿主能力请求相关执行者结束。
停止请求发出、代理确认、进程退出、上游任务结束分别核实；不要把取消显示当作执行终止。
保留有效成果和必要证据，说明哪些外部写入已经发生。补偿或回退按实际授权与数据状态进行。
取消某个尝试不取消整个用户目标；只有用户取消的范围停止，其他已授权部分继续。

## 4. 集成与多人审查

采用已有PR与评审规则；一个任务的done只表示可交回，不等于已经集成或发布。

1. 以接收时的任务/尝试、契约、BASE、候选和未提交内容核验身份。
2. 检查各分支修改的交集及语义冲突：接口、枚举、默认值、锁文件、生成物、迁移、权限和配置。
3. 按现有merge/rebase/cherry-pick策略集成，不统一强制某种历史策略。
4. 在共同候选上检查跨层行为，保留合并后的HEAD；必要时对新基线做相关回归。
5. 审查的批准只覆盖它实际审过的内容。后续行为变化与合并冲突解决需相应复核。
6. 对共享环境核实际运行产物，发布由该环境的既有负责人/队列执行。

跨机器交付使用接收方有权访问的提交、补丁或证据附件，并保留与候选的对应关系；仅给发送方的本地绝对路径不算可接收的交付。
记录足以定位结果的执行环境、输入范围与相关配置，日志和截图按项目规则脱敏；不要为审计上传完整聊天、密钥或无关业务数据。

GitHub的CODEOWNERS用于归属和审查路由；是否必须批准取决于实际分支规则。所需权限、身份、必需检查、可信检查来源和例外分别核对，不能从文件存在推断已经受保护。
多个模型使用同一账号不自动满足独立人员审批。审查者可以写自己的审查记录，但不擅自改被审实现或替它降低门禁。
[分支保护文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)还说明skipped/neutral可能满足required status checks；项目需要“实际执行”时，CI应产生明确的执行审计结果。
[Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)约束同仓库的匹配任务；它不自动覆盖本地命令或另一个仓库。迁移/部署应核取消策略，不复制测试任务的自动取消规则。

独立审查输入原需求、完整差异和原问题，允许零发现；新会话、新模型或新报告不能抹掉旧拒收。
修复循环有终点，预算耗尽时转为明确阻塞或范围决定；未完成关键验收不能被自动改名为完成。

## 5. 跨宿主真正可移植的部分

可移植的是任务目标、合同、代码与产物身份、问题账本和结果证据。下面的运行能力不能仅靠相同SKILL.md推断：

| 能力 | 使用前确认 |
| --- | --- |
| 子代理/团队 | 是否共享文件、上下文、任务列表；谁实际管理生命周期 |
| 工作树隔离 | 实际cwd/branch是否正确；命名agent、插件角色或调用方式是否改变隔离 |
| 技能加载 | 当前实际加载路径、名称和版本；子代理是否需要另行预加载 |
| 权限/审批 | 当前有效allow/ask/deny与继承方式；用户直接调用与模型派生是否不同 |
| 消息和恢复 | 发送成功、任务结束、会话恢复分别如何确认；本地消息是否跨工具可见 |
| hooks与门禁 | 何时触发、是否有执行记录；未支持时由既有CI/工具检查承担 |

Claude团队与subagent的上下文、隔离和配置继承有不同规则；其本地任务领取锁不代表跨harness的通用锁。OpenCode的工具与task权限也有自己的合并/匹配语义。按当前版本验证，不将这些细节硬编码成通用协议。

## 参考与采用边界

- [Git worktree](https://git-scm.com/docs/git-worktree)：隔离范围、共享配置与lock的真实作用。
- [GitHub CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)：归属与审查路由，结合实际分支规则使用。
- [Claude subagents](https://code.claude.com/docs/en/sub-agents)与[agent teams](https://code.claude.com/docs/en/agent-teams)：按任务选并行、实际核上下文/工具/隔离；不复制运行时team文件。
- [OpenCode permissions](https://opencode.ai/docs/permissions/)与[agents](https://opencode.ai/docs/agents/)：核实际有效工具权限，不照抄另一宿主配置。
- [Superpowers SDD固定快照](https://github.com/obra/superpowers/blob/22f0b463e7a5e579904dd6211a520321035526f7/skills/subagent-driven-development/SKILL.md)：采用窄任务、BASE/HEAD、进度账本与有限复核；不采用其统一串行实施、强制指定模型或停放关键问题后记完成的规则。

核查日期：2026-11-04。以上公共能力仍需对照使用中的版本；本协议不安装协调服务，不承诺分布式锁、可靠消息或跨宿主事务。
