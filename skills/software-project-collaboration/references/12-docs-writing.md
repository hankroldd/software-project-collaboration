## 输入与受众

明确文档是给开发者、接续代理、运维人员、业务使用者还是决策者阅读。
读取代码、配置、已有规格、实测记录和用户已确认口径。
把事实、设计目标、推测和待确认项分开，保留来源与适用版本。
先回答读者要完成什么任务，再决定是否需要技术细节。
“去 AI 味”是把意思说清楚、说准确，不能删除必要限制或专业定义。
没有素材的地方可写结构或明确缺口，不填编造的客户、数字、成效与测试结果。

## 文档单源

### 为每类信息指定唯一主位置

| 信息 | 主位置 | 其他文件怎样使用 |
|---|---|---|
| 项目目标、边界、入口 | `docs/PROJECT.md` 或既有项目说明 | 引用摘要与链接 |
| 当前进度与下一步 | `docs/STATUS.md` 或既有状态文件 | 不再维护第二份任务总账 |
| 约定的用户行为 | 现有 specs 或变更规格 | 需求编号和链接 |
| 当前实现与接口 | 代码、契约文件及对应说明 | 引用路径、版本与观察范围 |
| 为什么这样设计 | `docs/architecture/` 内 ADR | 引用决定，不重写论证 |
| 真实验证结果 | `docs/verification/` | 标出版本、环境和证据 |
| 部署、恢复、故障处理 | `docs/operations/` | 快速入口与适用范围 |

现有目录承担同一职责时沿用，不为了整齐搬迁或复制。
规格是行为约定，代码是实现现状；不一致时报告差异，不能自动宣称任一方总是正确。
文档中引用易变事实时记录核查日期、版本或提交；不能把过去结论写成永久能力。
README 保持快速开始和导航；AGENTS/CLAUDE 保留稳定规则与索引。
把旧决定标成已替代并链接新决定，避免两份文档同时声称有效。
删除历史文档前先确认是否有审计、发布或回退用途；可归档的保留可追溯链接。

## 写作步骤

1. 写出读者此刻最关心的结论、动作或状态。
2. 用真实业务名词替代泛泛的“能力”“体系”“全面提升”。
3. 每段说明一件事：发生了什么、为什么需要、怎么做或如何验证。
4. 把并列信息写成短表或列表，把有因果关系的信息写成连贯句子。
5. 把大段实现细节移到开发或运维说明，给业务读者保留输入、动作和输出。
6. 检查每个数字、状态与绝对判断，补来源或降为有条件的表述。
7. 最后按读者路径走一遍：是否找得到入口、理解动作、知道结果与失败后怎么办。

### 直接写动作和结果

| 空泛表述 | 更清楚的写法 |
|---|---|
| 全面赋能文件智能处理 | 上传文件后，提取指定字段并生成结果表 |
| 打造统一高效的协同闭环 | 在同一页面查看处理进度、修改结果并导出 |
| 显著提升系统稳定性 | 修复断线后重复提交的问题；已完成相应回归 |
| 深度优化权限能力 | 普通用户只能编辑自己的记录；越权请求会被拒绝 |
| 实现多维智能洞察 | 按日期、单位和问题类型汇总结果 |
| 已完成全面验证 | 写明实际验证的路径、版本与未覆盖范围 |
| 操作异常，请稍后重试 | 写明失败动作及可行下一步，隐藏无关内部堆栈 |

示例只说明表达方式，必须用当前功能的真实行为替换。
不要把“安全、稳定、高效、智能、无缝、全面”作为无证据的完成结论。
保留精确术语，例如事务、幂等、迁移、SSE；首次出现时用一句话解释其影响。
不能用“大白话”掩盖同步与异步、删除与停用、保存与发布的区别。

### 需求、方案与完成报告

需求写使用者、场景、输入、动作、输出、异常及验收。
方案写现状问题、约束、复用项、选择理由、需要改变的部分与代价。
完成报告先写结果，再写改变及原因、验证、剩余风险和下一步。
未发布时写“已实现并验证”，不能写“已上线可用”。
未测业务成效时写目标与测量办法，不能把工程测试通过换算成效率提升。
报告中的风险应具体关联当前变更，不附无关的通用安全免责声明。
PR 描述解释问题、改动与行为变化，列出足以评审的测试和兼容信息。
不把提交过程、工具次数和代理思考流水当作成果。

## 界面文案

### 按用户要做的事命名

按钮写动作，如“保存修改”“发布”“重试上传”“下载结果”。
同一操作在按钮、对话框、通知和帮助中使用同一个词。
区分保存草稿、发布、停用、退役、删除；后果不同就不能用同一模糊词。
业务页面只呈现用户需要作决定的信息，不展示内部工具名称、对象 ID 或实现路线。
调试细节放到日志或可展开的诊断入口，保留供支持定位的适当标识。
如果技术信息直接影响选择，例如文件大小限制或权限范围，应明确显示。

### 每个关键状态给可行下一步

| 状态 | 文案应说明 |
|---|---|
| 空态 | 当前没有什么、为什么可能为空、能做什么 |
| 加载/长任务 | 正在处理什么；有真实进度才显示百分比 |
| 成功 | 已完成的动作与结果位置 |
| 校验失败 | 具体字段、允许范围或示例，尽量就地显示 |
| 服务失败 | 哪一步失败、已保存内容是否保留、可用恢复动作 |
| 无权限 | 当前操作受限；如有正式申请途径，提供准确入口 |
| 破坏性操作 | 影响对象、后果、是否可恢复，使用真实动作名称 |

错误信息不许承诺后台一定重试或一定保存，除非代码确实做到。
没有真实进度时用阶段或等待状态，不能伪造平滑递增的百分比。
不让 UI 文案承担服务端权限校验；提示和实际行为必须一致。
尽量让标题、按钮、正文各做一件事，减少重复解释与装饰性标签。
不要为了简洁删掉用户做决定所需的限制与后果。

## 产物与验证

按变更范围更新唯一主文档及必要链接，不要求所有文档同步改一遍。
R0：核对错别字、排版、长文本、按钮宽度、移动或窄窗口显示。
R1：把文案中的动作、状态与实际代码路径对照，验证链接和操作入口。
R2：核对前后端、UI、API 与帮助使用相同术语和失败语义。
R3：权限、删除、迁移、模型能力、恢复承诺等关键文字必须对应真实行为证据。
技术步骤记录命令执行目录、前置条件、关键参数、成功信号和失败后动作。
引用命令可以用占位表示秘密；必须说明需要替换，不能给出看似可用的假凭据。
Markdown 检查标题层级、列表空行、表格列数、代码围栏和相对链接。
Mermaid 仅用于关系或流程确实更清楚时；优先基础语法、短标签和小图。
图无法确认能渲染时改用普通表格或步骤，不能把报错图当成已交付结果。
界面变化查看实际渲染与关键操作；文档代码示例只执行范围内安全且必要的命令。
在验证记录中说明检查了什么；未验证的命令或部署步骤明确标注。

## 反例与停止条件

- 不把所有专业词替换成含混口语，也不把一般按钮写成宣传标语。
- 不用“已解决所有问题”“百分之百可用”等超出证据的绝对表述。
- 不通过重写文档掩盖未实现的功能或失败的测试。
- 不把示例数字、压测条件与未经核实的第三方能力写成当前事实。
- 不让图、标题、卡片和口号代替关键业务内容。
- 发现文案承诺与实际行为冲突时，先保留证据并修正范围内的问题。
- 关键事实不可核实时，完成其他已知部分，把具体未知写清楚再请求必要输入。
- 面向用户的简短说明可以省略实现细节，不能省略重要未完成项。
