# 08 构建、发布与部署

目录：输入与授权｜冻结交付内容｜环境与离线包｜迁移与恢复｜执行发布｜验收与停止条件。

## 输入与授权

1. 明确目标环境、部署方式、当前版本、目标版本、维护窗口和成功标准。
2. 读取任务 BASE/HEAD、实际工作树、已完成验收、遗留问题及项目发布门禁。
3. 沿用仓库 L1–L3 等既有规则并映射风险；发布、迁移按 R3 处理相关风险。
4. 区分本地构建、隔离演练、共享测试与生产切换，不默认把修改代码授权扩展到生产。
5. 现有授权已覆盖目标操作时继续执行，不重复要求用户确认。
6. 生产动作尚未授权时，先完成包、差异、验证和恢复方案，再呈现具体待执行动作。
7. 不以本文件新增逐阶段审批；权限边界来自实际任务和系统规则。
8. 不代用户通知客户或团队；发送消息需要已有明确授权。

## 冻结交付内容

建立可追溯链：源码→构建产物→镜像/安装包→环境配置→迁移→运行实例→验收记录。

| 清单项 | 至少记录 |
|---|---|
| 源码 | 仓库、任务 BASE、目标 HEAD、实际工作树与补丁/内容指纹 |
| 构建 | 命令、工作目录、锁文件、工具版本、时间、退出码 |
| 产物 | 文件名、SHA-256、大小、适用架构；镜像另记 ID/可用 digest |
| 配置 | 配置版本、必填变量名、默认值策略、目标差异；排除真实秘密 |
| 数据 | 当前/目标 schema、迁移顺序、兼容范围、恢复点 |
| AI 依赖 | Dify、插件、模型、提示词、工具、知识库/Workflow 的对应版本 |
| 验证 | CI 对应 commit、测试发现/通过/失败/跳过数、业务验收证据 |

交付未提交工作树时必须如实记录差异；不要把同一 HEAD 下不同内容当同一发布版本。
需要可复现发行版时，先将批准范围保存为明确版本，再从该版本构建。
本次包与已测试包不同时，重做覆盖差异的验证，不复用不相干的通过记录。
固定实际所需依赖版本；不为“保持最新”同时升级无关依赖或基础镜像。
不要直接运行未经审查的社区安装脚本或 `curl | sh`。

## 环境与离线包

### 先盘点现有环境

- 识别宿主机 OS/CPU 架构、Docker/Compose、设备运行时、可用磁盘和关键目录。
- 绘出最小运行关系：入口、前端、API、存储、Dify、模型和必要第三方服务。
- 列容器端口、宿主机映射、反向代理路径、内部服务名与对外基址。
- 识别数据库、上传文件、生成文件、知识库、插件和模型的持久卷/挂载。
- 检查目录权限、UID/GID、时区、DNS、证书和离线资源引用。
- 读取结构性配置时避免输出完整环境变量、凭据或含秘密的连接串。
- 优先复用已有 Compose 和服务；新增容器须解释其不可替代的作用与维护成本。
- 不假设在开发机可启动就代表客户现场可启动。

### 组装离线材料

| 类别 | 核查点 |
|---|---|
| 镜像 | 明确 tag、架构、ID/可用 digest 与归档 hash；避免浮动标签决定版本 |
| 应用 | 包含真实构建产物与迁移；不要依赖宿主机未声明的源码或缓存 |
| 依赖 | 按实际需要包含 Python/npm 包、OCR、字体、模型、插件等 |
| 配置 | 提供无秘密样例和变量说明；单独说明凭据的现场注入方式 |
| 脚本 | 安装、启动、停止、升级、状态查看、恢复；先检查再修改，失败可诊断 |
| 文档 | 前提、端口、目录、版本、运行命令、验收、常见故障、恢复步骤 |

Docker `save/load` 传输镜像；业务卷、数据库和模型挂载另行处理。
区分归档文件 hash、镜像 ID 和 registry digest；不要把不同概念误作相等检查。
导入后核对预期镜像、架构与应用版本；没有可用 RepoDigest 时记录其他可靠标识。
离线演练禁止悄悄联网补依赖后宣称离线安装通过。
重复运行安装/升级脚本应按设计安全处理已存在资源，不能覆盖未知现场数据。

## 迁移与恢复

### 明确变更性质

1. 列新增、重命名、删除、回填、索引和默认值变化，以及旧应用的兼容性。
2. 对长时间或大批量迁移估计锁、耗时、磁盘、失败中间态和重入方式。
3. 可以分步时先保持兼容，再切换读写，最后独立清理；按实际风险选择步骤。
4. 在隔离且具代表性的数据上演练，检查行数、约束、归属与关键查询。
5. 不把“应用镜像回滚”写成“数据一定可回滚”；二者分别给路径。

### 备份与恢复点

- 写明数据范围、备份方式、目标位置、权限、校验、时间和保留策略。
- 对数据库使用适配数据库的备份/快照方式；不要直接复制运行中的数据目录当可靠备份。
- 将数据库、文件和其他持久资产的一致性要求写清楚，避免恢复后引用断裂。
- 在隔离环境恢复并核对关键数据、文件关联、权限和业务路径。
- 记录实际恢复耗时与可接受数据损失窗口；没有实测就标为计划值。
- 需要密钥才能恢复时，核实授权人员可取得密钥；不要把秘密写入发布材料。

### 回退计划

- 定义触发条件：关键路径失败、迁移失败、错误率/延迟越界或数据不一致等。
- 给出旧包、旧配置及数据库兼容要求，明确谁执行、执行什么、如何验收。
- 发布后已有新写入时，先评估恢复备份的数据损失；不能机械覆盖当前数据库。
- 对不可逆动作明确恢复或前向修复路径，不能承诺不存在的一键回退。
- 在既有授权内做止损；超过范围时先准备具体选项和影响，再请求必要决定。

## 执行发布

### 发布前

1. 再核对目标主机/环境、当前版本、操作范围与准备好的包。
2. 核对必需门禁；失败、未触发和 skip 分别解释，不能用“CI 绿了”概括缺失检查。
3. 核对备份/恢复证据、剩余容量、依赖就绪和端口冲突。
4. 保存当前运行配置的安全摘要与版本标识；不要暴露配置秘密。
5. 确定业务写入/任务排空策略；不要在长任务中途无说明地重启依赖。

### 发布中

1. 按已演练顺序执行，记录步骤、命令、返回结果和实际时间。
2. 对失败及时停在可诊断状态；不要用连续重试掩盖迁移或配置错误。
3. 将容器 running、服务 ready、依赖 ready、业务可用分开检查。
4. 使用明确健康条件；单纯 `depends_on` 启动顺序不保证依赖已可服务。
5. 核对后端 API、代理路径、文件访问和模型调用，不只查看首页。
6. 记录运行容器/进程实际版本，确认与本次包一致。
7. 保留有用日志，删除/收回测试凭据和测试业务对象时遵循既定清理范围。

### 发布后

- 执行一条代表性的正式入口路径，并覆盖本次变更的高风险行为。
- 检查保存回读、旧数据/旧会话、文件访问及必要的权限反例。
- 观察预定窗口内的错误、延迟、资源、队列和关键任务；记录实际窗口长度。
- 涉及开机自启时，在授权条件下验证主机重启与服务恢复，否则明确未验证。
- 不把测试环境部署写成生产已发布，不把页面更新写成全体服务已升级。
- 将运行状态、剩余问题和后续运维入口交给既有负责人；不擅自发送外部通知。

## 验收与停止条件

输出一份发布记录：范围、版本/产物、环境、执行结果、业务验收、回退状态、遗留问题。
明确结果为已构建、隔离演练通过、已部署到指定环境、受阻或已回退中的哪一种。
备份无法验证、关键门禁失败、目标不明或包版本不一致时，停止相应高风险动作。
未获生产授权时完成可审阅结果，并说明具体待授权步骤，不声称发布完成。
已达成目标且观察窗口满足时停止额外变更，不顺带重构生产基础设施。
