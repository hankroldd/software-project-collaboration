## 输入与盘点

确认目标仓库绝对路径、项目用途、最短用户路径和预期运行环境。
先用 `rg --files` 找说明、项目清单、锁文件、测试、CI、容器和部署配置。
读取根目录和相关子目录的 `AGENTS.md`、`CLAUDE.md` 及它们实际引用的规则。
检查当前分支、HEAD、工作区修改和已有工作树；保留用户未完成的工作。
识别这是空仓库、可运行存量项目、半成品，还是只缺文档的项目。
读现有启动和测试命令，记录能运行与尚未验证的部分。
明确数据库、外部服务、模型、文件目录与端口的真实依赖；不能只凭 README 推断。
区分应用运行依赖和开发工具依赖，避免把开发工具安装到交付镜像。
没有代码访问权限时，可建立接入方案；不能声称完成了源码盘点。

## 选择接入方式

| 情况 | 处理 |
|---|---|
| 已有清楚的 docs 与规范流程 | 建路径映射并补缺项，保留原目录与名称 |
| 已有 OpenSpec / Spec Kit | 把项目上下文、状态、运维与验证链接接入原流程 |
| 存量代码较多而文档不足 | 先记录现状与关键链路，逐步补充，避免大规模重排代码 |
| 真正空项目，目标简单 | 使用 minimal 文档骨架和一个能跑通的纵向功能 |
| 多层应用或多人长期协作 | 使用 standard，补接口、部署与接续约定 |

`minimal` 与 `standard` 是文档骨架深度，不代表强制增加框架、数据库或容器。
选型沿用已确认约束；有现成栈时不因个人偏好改成其他语言或 UI 库。
没有既有栈时，比较最少的合理候选，说明维护、部署和人员成本后作出判断。
版本、兼容性和官方初始化命令必须核对当前官方资料，固定实际采用版本。
不要让项目初始化自动包含登录、Redis、消息队列、Kubernetes 或通用插件系统。

## 初始化步骤

### 1. 建立可恢复基线

记录仓库、分支、HEAD 与未提交变更范围；新仓库注明尚无提交。
已有工作区可直接使用；需要并行隔离时才建立独立分支/工作树。
共享配置、数据库与服务端口不会随工作树自动隔离，另行确认。
不使用清理命令删除未知文件，不把已有未提交修改作为“脏环境”自动丢弃。

### 2. 预览文档骨架

使用本 skill 的脚本，从明确的目标路径生成预览：

```bash
python3 "<skill-root>/scripts/bootstrap_project.py" --root "/abs/project" --name "example" --tier minimal
```

检查计划新增的文件是否与既有规范重复，是否落在正确仓库。
`<skill-root>` 应替换为本 skill 的真实目录，不把示例占位路径原样执行。
预览是防误写步骤；用户已要求初始化且预览无冲突时，直接应用：

```bash
python3 "<skill-root>/scripts/bootstrap_project.py" --root "/abs/project" --name "example" --tier minimal --apply
```

脚本默认不覆盖已有文件；现有文档的补充应先读取，再作小范围编辑。
遵循脚本实际输出；“已创建骨架”不等于“文档内容已完整”。

### 3. 填写项目真实约定

把入口、依赖、运行方式、目录职责、权限与数据边界写成能核查的事实。
记录每条常用命令的执行目录、必要环境变量名称、结果与适用环境。
不写真实密钥；提供环境变量样例时使用明显占位并解释是否必填。
同一语言保留一个明确包管理器和对应锁文件，不无故引入第二套工具。
保留语言/运行时版本约束；镜像或离线包记录精确版本与来源。
规定接口、配置、迁移、UI 变化分别更新哪份文档，不要求每次更新所有文件。

### 4. 建最小可运行切片

从一个真实用户动作开始，实现界面或入口、服务处理和结果反馈的完整路径。
需要持久化时验证保存与重新读取；不需要时不先建数据库。
接口返回真实结构，错误可识别；演示数据显式标记，不能伪装真实服务成功。
已有共享组件、HTTP 客户端、错误处理和权限设施时复用。
长任务才加取消/超时/进度；根据实际负载决定是否需要队列或后台进程。
保持前后端契约可见：字段、空值、时间、错误码、分页及上传边界。

### 5. 放入必要工程检查

采用仓库现有 lint、类型、测试和构建命令；新项目选择最少且能发现真实错误的检查。
让本地与 CI 使用同一条受维护命令；没有 CI 平台需求时不先生成多平台工作流。
确保失败命令能返回失败，不能用吞错或宽泛跳过制造全绿。
第一条测试应覆盖核心行为或已识别风险，不为目录完整写空测试。
配置依赖安装、构建、运行与测试的独立入口，避免“一个脚本顺便部署生产”。

## 文档与目录

| 位置 | 记录什么 | 更新触发 |
|---|---|---|
| `docs/PROJECT.md` | 目标、用户、边界、当前栈、入口、关键约束、文档索引 | 产品边界或基础事实变化 |
| `docs/STATUS.md` | 当前任务、已完成证据、阻碍、下一步、HEAD/环境 | 完成有意义步骤或交接 |
| `docs/architecture/` | 当前组件关系、数据流、重要决策及 ADR | 结构、契约或长期决策变化 |
| `docs/changes/` | 本次行为规格、计划、任务与取舍 | 新功能、重要修复或范围变化 |
| `docs/verification/` | 验收对象、版本、操作/命令、结果、限制 | 完成验收或关键复测 |
| `docs/operations/` | 部署、配置、备份恢复、故障和回退 | 运行方式或发布流程变化 |
| `.engineering/project.json` | 工程工具可读取的项目配置 | 命令或接入配置变化 |

已有同职责文件时在索引中映射，不复制一份新内容。
`README.md` 只保留项目介绍、快速启动和入口链接，详细规范放到对应位置。
`AGENTS.md` 只保留跨任务稳定规则与模块索引，不放变更流水账。
Claude 与 Codex 的入口文件引用同一份核心约定；按实际宿主支持方式配置。
不要假定宿主能自动识别另一个工具的目录、斜杠命令、hooks 或工具名称。
机器配置是数据，先理解字段及来源，不把任意字段拼接成可执行 shell。
把生成文件、缓存、测试证据、真实数据和密钥按项目需要排除，避免宽泛规则漏收源码。

## 验证与交付

按实际风险检查；文档骨架初始化通常无需新建测试套件。
R0：查看排版、链接和命令占位是否明确，确认没有改变行为约定。
R1：执行实际快速启动和最小检查，确认路径、锁文件与命令一致。
R2：打通一个跨层用户路径，检查错误与回读；记录外部依赖未测部分。
R3：若涉及权限、迁移或发布，再执行对应模块的契约、恢复与运行检查。
新项目从干净环境复现启动最有价值；存量项目优先验证新文档描述的路径。
验证服务能启动与核心业务能成功是两项证据，不能只看进程存在。
交付时列出新增/补全文件、实际运行命令、环境、结果和未完成项。
把确定的下一步写进 STATUS，避免下一会话从头搭建相同基础设施。
不要宣称已经部署，除非已在指定目标运行并完成相应验收。

## 反例与停止条件

- 不把“初始化良好”解释成所有工程目录、平台和中间件都先建齐。
- 不用通用模板覆盖已有 README、AGENTS、CLAUDE、许可证或部署配置。
- 不把测试命令、端口、数据库类型与路径从常见项目猜进文档。
- 不把模板中的示例项目名、账号、指标、目标版本当成已确认事实。
- 不因初始化方便绕开仓库已有发布或依赖来源限制。
- 发现目标路径错误、用户改动冲突或配置与运行事实不一致时，先解决定位问题。
- 必要外部服务不可达时，交付已完成骨架与明确阻碍，不伪造成功输出。
- 只有明确授权的动作超出当前能力或涉及未授权不可逆变化时，才停在该动作前。
