## 先固定问题与现场

接收用户动作、预期、实际、首次出现时间、影响范围、可复现输入和运行环境。
先区分故障严重度 S0–S3 与修复风险 R0–R3；严重故障也可能只需很小的修复。
安全或可用性事故先执行已授权的止损措施，同时保留必要现场；不等长篇分析才行动。
记录源码 HEAD、子模块、镜像/进程版本、配置来源、数据库版本和实际入口。
不要把“本地已改”“服务已重启”和“目标环境已运行该代码”当成同一事实。
保存最小脱敏复现材料、关键错误和时间线；避免复制整库、真实正文和所有日志。
从用户当前失败路径复现一次，写出稳定步骤；无法复现就标明条件差异。
不要先清缓存、重建容器或删数据而丢掉定位所需证据。
普通已授权诊断和可逆修复继续推进；需要影响生产或不可逆数据操作时确认具体动作。

## 沿真实调用链定位

按一次操作的实际顺序检查，不凭最后一行错误猜根因。

| 层 | 先核什么 | 常见误判 |
| --- | --- | --- |
| 页面 | 控件状态、请求是否发出、渲染和生命周期 | build 成功就认为页面可用 |
| API 客户端 | base URL、认证、拦截器、信封和类型 | 把 body 当 response 再解包 |
| 路由/授权 | 是否命中、真实身份、角色、资源范围 | 前端能看到就认为服务端允许 |
| 服务/作业 | 分支、状态、重试、幂等和超时 | 断连就认为任务失败 |
| 数据/文件 | 事务、版本、路径、挂载、历史和持久化 | 文件生成就认为用户能找到 |
| 依赖/网络 | 锁定版本、地址、端口、证书、连接与缓存 | 容器内 localhost 当宿主机 |
| 构建/发布 | 镜像输入、测试收集、实际执行、部署身份 | CI 绿就认为镜像与代码一致 |

AI 功能再分 Data、Context、Tool、Planner、Executor、Harness 六层归因。
区分输入材料缺失、检索范围错误、工具失败、规划错误、执行错误和评测本身错误。
模型写出了材料中没有的事实时，保留原文与输出对应证据；不能只看调用是否成功。
不要用改提示词代替数据、权限、解析器或运行状态的修复。

## 用假设与反证缩小范围

一次列出少量可证伪假设，按成本最低且信息量最大的验证顺序执行。
每个假设写“若为真应看到什么、怎样排除、实际结果”。
优先对照成功与失败路径、旧版与候选、真实上游与替身、本地与目标环境。
只改变一个主要变量，避免同时升级依赖、重构界面和改配置后无法解释原因。
同一错误在多个入口出现时，先查公共层；同名字段多处定义时先找权威来源。
需要查看敏感配置时只读取定位所需的名称、存在性或脱敏值，不输出凭据。

按问题选择探针：

- 接口信封：截取脱敏真实 body，检查拦截器返回值，再执行一次页面渲染断言。
- 切页丢状态：核对路由、组件 name、缓存 key、激活/停用钩子及刷新来源。
- 并发覆盖：让两个客户端读取同一版本再提交不同更新，检查冲突或合并结果。
- 超时后重复写：核对第一次写入是否完成，再检查幂等重试与状态查询。
- 文件找不到：沿创建路径、登记记录、会话标识、权限、预览/下载逐段核对。
- 重启仍失败：查持久卷、容器可写层和启动标记各自生命周期，区分 restart 与 recreate。
- CI 未执行：核对触发条件、collect 结果、JUnit 实际执行、skip 和 job 依赖。
- 数据库差异：在目标数据库检查事务、排序、JSON 与并发行为，不以 SQLite 结果代替。

定位时保护用户范围；用户只给一个文件或数据范围，不自动扩大到全部资料。
外部服务不可用时，先验证已知合同和本地部分，明确被阻塞的层，不伪装真实集成。

## 实施最小修复

先写清导致问题的条件和应恢复的不变量，再修改代码。
把临时止损与根因修复分开记录：止损可以恢复服务，但不能自动关闭根因问题。
临时措施写适用环境、有效期/退出信号、遗留风险和负责事项。
从最小修改层处理，优先修共同根因，不在每个调用方各加一个补丁分支。
确需修改多个消费者时，列出全部路径并逐一核对，不只修当前截图对应页面。
保留原本正确行为；不要通过隐藏错误、丢弃失败事件或删除历史来制造成功外观。
避免空 catch、静默回默认值、无限重试和没有恢复入口的永久失败标记。
安全边界应拒绝时仍拒绝；恢复机制不能把故障模式改为无条件放行。
配置修复要沿声明、解析、脚本传参、容器环境、消费者和文档完整接通。
合法 `0`、`false`、空值、null 与缺省的判断必须按合同，不能统一走 truthy。
异步状态修复至少考虑成功、失败、写成功后读失败、中断及迟到响应。
权限修复同时检查允许与拒绝路径，避免“修越权”后把合法用户全部锁住。
数据修复先确认备份、范围和可恢复性；诊断授权不自动包含批量修改生产数据。
不要为了修一个故障顺带重构整个模块、迁移架构或增加容器。

## 验证与交接

对逻辑故障建立能触发原缺陷的最小回归；纯文字或低影响样式问题可用直接复核。
验证原触发条件已经修复，同时检查共享调用方和相邻状态。
关键断言要有判别力：可通过旧版本、受控反例或临时故障注入证明它会检出问题。
使用独立临时副本或测试机制做故障注入，不改用户工作区或生产环境来制造失败。
复跑与风险相匹配的检查，不因一次修复无限扩大测试。
真实集成、浏览器和目标环境仍有具体风险时再扩展验证。
把结果分成已通过、失败、跳过、未执行、环境阻塞；零收集不算通过。
声称“既有失败”时，给出基线版本、相同命令和同类环境的失败证据。
不能仅凭错误名字相同，就把当前失败归入旧问题。
构建、测试、合并和部署对象不同，记录差异并补必要检查。
审查发现修复后，按原问题和增量 diff 复核；保留原意见和未解决项。
不要更换审查会话以清除问题；需要独立审查时仍交付原始问题与证据链。

交付一个短修复记录：

| 字段 | 内容 |
| --- | --- |
| 问题 | 谁在什么操作中受到什么影响 |
| 根因 | 触发条件、错误所在层和证据 |
| 改动 | 修改位置与恢复的行为 |
| 验证 | 候选身份、命令/动作、结果和原始证据 |
| 边界 | 未覆盖环境、剩余故障和临时措施 |
| 发布 | 是否已集成、构建、部署及必要恢复方式 |

## 反例与退出条件

不得只重启后说“已修复”；除非已证明根因只是需重启生效且不会复现。
不得把静态源码断言通过写成真实 UI 或端到端验证。
不得让所有替身按当前实现返回，再据此认定上游合同正确。
不得把模型生成成功、文件可打开写成内容准确或业务验收通过。
不得改门禁、降低阈值或扩大例外名单来掩盖候选缺陷。
门禁误报应单独证明并按现行权限修复；合法跳过必须带理由，不能静默判绿。
同一假设被反证后换定位方向，不继续叠补丁；反复失败时回到调用链和环境差异。
出现范围扩大、无法恢复的数据变更或缺少关键访问时，完成可验证部分后报告具体阻塞。
当原问题、受影响链路和必要门禁已有充分证据后停止额外检查，推进已授权集成和交付。
