## 接手与开工

接收当前需求、验收标准、风险级别、设计决定、允许改动范围和仓库入口。
阅读有效 AGENTS/CLAUDE 入口与相关路径的约束；不要从旧会话推断当前授权。
先检查 `git status`、分支、HEAD、子模块指针和运行服务身份。
保留用户未提交改动；遇到重叠修改先隔离自己的工作，不覆盖或删除他人成果。
执行前确认项目既有 Git 策略；不要统一套用 rebase、squash、merge 或强推。
已有 L1–L3 分级时保留其含义，按任务入口映射到本体系，不自行改名降低门槛。
R0/R1 直接做必要修改与检查；R2/R3 先确认接口、状态、数据或权限合同已足够明确。
把一次实现的完成条件写成用户可观察结果，明确本次不承担的需求。
普通已授权工作持续推进；缺信息时先查可用源码和证据，再问真正影响结果的问题。

## 按纵切片实现

从最短的可用路径开始：入口 → 权限 → 操作 → 持久化 → 反馈 → 再次读取。
先完成这一条路径，再扩展批量、更多角色或更多输入类型。
不要把“前端完成、后端以后接”登记成可交付功能。
修改前搜索导出接口、直接调用方、事件消费者和测试；不要只读报错行附近。
接口变化覆盖所有调用方，尤其父子仓、历史加载、刷新恢复、导入导出和管理入口。
沿用模块现有风格和依赖；未坏的代码不顺手重构。
优先调用已有配置、组件、适配器、库函数和上游接口。
为本次真实需求增加最小代码；不预埋未经要求的平台化能力和扩展字段。
新抽象应说明至少两个真实消费者或必须稳定的边界；单个消费者通常先直接实现。
可用一把锁解决时不要先分片；单一状态版本足够时不要叠多层代次。
规则、转换和格式化优先确定性代码；只把需要判断、抽取或起草的部分交给模型。
文件过长时按真实职责拆分，不为凑行数把紧密逻辑分散到难追踪的小文件。
对有意简化的设计留下边界和升级信号，不把临时方案伪装成通用能力。

## 值、状态与并发

用显式条件处理边界，避免 `value || default` 抹掉合法的 `0`、`false` 或空字符串。
只有合同把 `null` 和缺省都定义为未设置时，才用空值合并等简写。
校验放在信任边界；内部可信对象不要层层重复检查产生不同错误语义。
解析、权限、业务校验、持久化的顺序应有依据；失败不能留下未说明的部分写入。
请求体仅更新被提交的字段；避免整对象覆盖他人的并发修改。
数据库优先用现有事务、唯一约束或版本条件，失败返回可处理的冲突。
重试前确认幂等性；不能对支付、发布、删除、生成任务等写操作盲目重复执行。
幂等键绑定同一业务操作，并明确超时后查询、重试、冲突与过期行为。
重复事件、乱序事件和终态后事件必须按合同处理，不能靠前端最后收到什么决定结果。
后台作业的任务状态与浏览器连接状态分开；断连不默认杀任务，取消须有服务端结果。
资源显示名与稳定标识分开；改名不生成新 ID，删除不绕过历史引用约束。
用户、租户、所有者、共享范围和当前执行身份逐层透传，不能只以“已登录”代替授权。
权限判断复用权威入口；隐藏按钮、开发者 URL 参数和缓存状态均不是安全边界。

在实现提交前核对这组常见遗漏：

| 边界 | 最小核对 |
| --- | --- |
| 值 | `0`、`false`、空值、null、缺省各有正确含义 |
| 异步 | 失败、取消、超时、写成功后读失败都能恢复 |
| 并发 | 同版本双写、重复提交、迟到响应不会覆盖新状态 |
| 权限 | 允许与应拒绝两侧，以及角色变化后的行为 |
| 生命周期 | 新建、编辑、停用、删除/退役、历史读取按合同一致 |
| 文件 | 存储位置、会话归属、持久化、预览和下载贯通 |

## 依赖、数据与上游

新依赖先核对已有能力、版本兼容、维护情况、许可证、体积和离线取得方式。
更新声明与锁定文件时使用仓库指定工具和参数；不手改生成锁来掩盖漂移。
本地、CI 和镜像的运行时版本应一致或有明确支持矩阵。
新增服务或容器前说明为什么现有模块无法承担，以及部署、监控、升级和备份成本。
新增 schema 时覆盖空库、旧库、重复 seed、升级失败和已有数据读取。
字段文档和类型能够从 schema 生成时保留唯一生成源，生成物不人工另改一份。
敏感数据与真实凭据不进入测试夹具、仓库、调试日志和构建产物。
避免让环境继承悄悄开启外部追踪；按现有产品要求验证运行时出站行为。
复用上游前读锁定版本的调用链；记录公开接口、挂钩、fork 补丁的边界。
只修改批准的上游范围；实现遇阻时不得自行扩大允许清单。
父仓提交子模块指针前确认目标提交可从指定远端取得，并满足现有准入规则。
分别记录“子仓已实现”“父仓已接入”“镜像已构建”“目标环境已部署”。

## 并行与集成

按可独立验证的子任务分工，明确输入、允许路径、产物和接口负责人。
写代码的工作单元使用项目允许的隔离分支或工作树；同一文件只设一个合并负责人。
共享规范、状态看板和需求账本由协调者汇总，避免多个代理同时重排覆盖。
调查、实现、审查和验收分工以能力和上下文独立性为准，不把模型品牌当质量证明。
审查者拿到基线、候选、规范和原始证据；不要先传递“已经通过”的结论。
保留原审查问题和处置链；不能更换会话来清除拒收或未解决意见。
控制构建、浏览器、模型和数据库并发，避免各自通过却把共享环境挤坏。
每个验证结果记录实际工作目录、提交、运行目标和命令。
集成完成后检查受影响调用链；合并结果不同于已测候选时，补相应验证。
测试在哪棵树执行，就明确关联哪棵树；不得拿 A 树的结果给 B 树提交背书。
收尾时列出已提交、未提交和未跟踪文件，不为“干净”强行提交无关用户修改。

## 验证、产物与反例

选择能证明需求的最小充分验证，而不是盲目增加测试数量。
业务逻辑和故障修复需要有判别力的用例；可逆的纯文字或样式修改无需机械补单测。
测试先表达业务意图或故障触发条件，再检查实现；关键用例应能检出相应缺陷。
使用替身时核对真实上游结构；权限、迁移、并发或发布等高风险保证需要对应真实环境证据。
区分静态检查、单元、组件、API 集成、浏览器与目标环境验证，分别报告结果。
缺依赖、零收集、skip、环境失败都不能写成通过；已知失败要有同条件基线依据。
不要删除断言、放宽错误集合或修改门禁，仅为了让当前候选通过。
如门禁确有缺陷，给出最小复现和正确判据，按现行权限修复后重新验证，不伪造放行。
文档只更新受影响的需求、合同、运行步骤和当前状态；历史原始证据保留身份，不反复复制。
交付说明写清改动原因、行为变化、验证、未验证及必要的恢复方式。
不以“编译通过”“测试很多”“AI 审查通过”单独证明业务可用或正式发布。

完成前检查以下反例是否出现：

- 只修一个入口，历史页、管理页或后台执行仍使用旧判断。
- 保存接口返回成功，但页面丢失状态或生成文件在会话里找不到。
- 为一次需求新增通用框架、第二套权限系统或额外容器。
- 实现扩大范围后修改 spec，让原本不合格的候选显得合格。
- 测试、提交、构建、部署分别来自不同版本而未说明。
- 用户只要求实现，交付却只有目录、长计划和准备材料。
