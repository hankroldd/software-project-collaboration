# 07 测试、验收与代码审查

目录：输入与边界｜选择验证｜执行与取证｜代码审查｜高价值场景｜交付与停止条件。

## 输入与边界

1. 读取任务目标、MUST/SHOULD/COULD/DEFER 范围、验收条件和已确认的业务决定。
2. 读取任务 BASE、当前 HEAD、工作树状态、相关 spec、项目测试命令与 CI 门禁。
3. 沿用仓库已有 L1–L3 口径，记录其与本次 R0–R3 的映射，不另造同名等级。
4. 根据风险选择验证深度；需求优先级、实施风险和缺陷严重度分别记录。
5. R0 文案/样式小改以检查实际结果为主，不机械新增测试或完整 spec。
6. R1 局部行为做相关用例；R2 跨层变更覆盖契约、状态与集成路径。
7. R3 权限、迁移、发布、模型事实等按实际风险增加反例、恢复或业务评测。
8. 现有项目必需门禁仍须执行；不擅自把失败、skip 或未发现测试改称通过。

## 选择验证

先写“哪一种失败会损害此次目标”，再选择能发现它的检查。

| 检查 | 验证对象 | 主要限制 |
|---|---|---|
| 静态/类型/构建 | 语法、类型、依赖、可构建性 | 不证明用户流程可用 |
| 单元/组件 | 独立规则、边界值、组件状态 | 不证明真实存储与多进程竞争 |
| 契约 | 请求、响应、错误、事件、兼容性 | 不证明模型事实正确 |
| 集成 | 实际适配层、事务、权限、持久化 | 不证明界面可达和可读 |
| 浏览器业务路径 | 入口、操作、保存、回读、运行 | 不覆盖所有规模与环境 |
| 视觉/交互 | 滚动、焦点、长文本、弹窗、状态 | 截图不能证明数据保存 |
| 部署冒烟 | 指定交付版本的代表路径 | 不替代恢复演练和完整评测 |
| AI 业务评测 | 给定样本的事实、效果、工具行为 | 不代表未测试任务普遍可靠 |

按依赖关系定位影响范围，包括调用方、持久数据、旧会话和下游展示。
已有用例能有效覆盖时直接复用；新增用例优先固定真实缺陷与关键不变量。
不要编写只重复实现、检查源文件包含某字符串或仅检查 mock 被调用的装饰性测试。
对稳定且重要的业务规则可先写失败用例；不要为流程形式反复重写无风险内容。
项目没有某类门禁时，说明缺口并做当前可行检查，不虚构既有测试能力。

## 执行与取证

### 先标明测试对象

- 记录仓库、分支、任务 BASE 和被验证 HEAD；BASE 是任务起点，不随便替换成最近提交。
- 同时记录实际测试工作树：已暂存、未暂存、未跟踪文件及补丁/内容指纹。
- 工作树有修改时，单独 HEAD 不能准确标识被测代码；禁止只填 HEAD 冒充已提交版本。
- 记录测试目录、配置、依赖版本、测试数据来源及真实依赖与替身的边界。
- 测试构建包/容器时，记录构建产物 hash、镜像 ID/可用 digest 与运行实例对应关系。
- 运行环境与本地代码不能确认一致时，把该证据限定为环境观察。
- 后续归档证据产生的提交与被测候选分别记录；不把归档后的新HEAD改填成旧测试对象。只有证据文件变化时说明差异与等价范围，行为相关内容变化时补对应验证。

### 运行检查

1. 从仓库实际脚本读取命令，使用正确工作目录和锁定依赖；不猜测脚本名称。
2. 先运行能直接覆盖改动的检查，再运行项目必需门禁。
3. 记录完整命令、退出码、开始/结束时间、发现/执行/通过/失败/跳过数量。
4. 对预期存在测试而发现数为零的情况，排查收集配置；不能记录为业务通过。
5. CI 缺失、取消、未触发、skip 与失败分别说明；检查绑定的 commit 是否正确。
6. 失败时区分改动引入、既有失败、环境阻塞和不稳定测试，并给可复核依据。
7. 不通过放宽断言、跳过关键用例、提高重试次数或删除测试制造通过结果。
8. 修复后运行直接受影响的检查；只有剩余风险或既有门禁要求才扩大回归。
9. 若重跑后通过，保留第一次失败及判断，不隐藏不稳定性。
10. 最后核对工作树是否又改变；改变了被测内容就更新相应证据。

### 浏览器验收

- 先观察实际 DOM/可见状态，再使用 role、label 或稳定 test id 操作。
- 等待明确业务状态或可见断言，不一律等 `networkidle`，不靠固定延时掩盖竞争。
- 对持久化操作完成“操作→保存→重新获取/刷新→再次进入”，必要时核查实际数据。
- 对发布功能完成“编辑→保存回读→发布→正式入口运行”，记录版本。
- 以真实可访问的实例验证；模拟 UI 必须标为模拟，不能冒充目标环境验收。
- 按影响覆盖正常、空、错误、权限不足、长文本、加载、未保存、取消等状态。
- 检查滚动容器、固定头尾、窄高度、弹窗和焦点；保存按钮必须可到达。
- 失败时保存必要截图、trace、浏览器错误和失败请求；清理凭据与敏感业务内容。
- 将截图绑定页面、状态、步骤和代码/运行版本；不把一张静态截图称为全链路通过。

### 服务端验证

- FastAPI 异步测试须确认 lifespan、连接池与启动资源确实建立并释放。
- 关键持久化与权限用例使用隔离的真实存储；mock 测试另列其证明范围。
- 并发用例使用独立客户端与可控同步；避免靠随机 sleep 猜测竞争。
- 验证多 worker 情况时，检查数据库事务/唯一性/版本控制，而非只看进程内锁。
- 失败/取消后的资源、临时文件和半完成记录按契约清理或保留。

## 代码审查

1. 阅读任务 BASE 到目标 HEAD 的实际差异，同时覆盖未提交修改与相关上下文。
2. 先对照 spec 核对行为，再审查权限、数据、异常、并发、兼容、性能与维护成本。
3. 检查调用方、配置、迁移、发布脚本及测试是否与实现一致。
4. 审查结果优先写可复现缺陷和实质风险，不用个人代码风格偏好充数。
5. 每项发现写明 S0–S3、文件位置、触发条件、错误行为、影响和证据。
6. 将已证实问题、待验证疑点、建议明确区分；没有发现就如实写没有发现。
7. 需要独立复核时提供任务、原始 diff/spec/日志，不提前告诉审查者期待的答案。
8. 主负责人仍须阅读关键代码和验证证据，不能用新开一个对话替代审查责任。
9. 处理意见后复查实际改动；“已按意见修改”不是证据。

用户要求最近 7 天审查时，列出起止时间、分支、提交集合与逐项审阅覆盖。
使用 `repo_snapshot.py` 获取只读快照与清单；清单生成不等于代码已经审查。
任务差异与 7 天清单分别保留，不能相互替代，也不能只看提交标题作结论。

## 高价值场景

| 场景 | 必须观察的结果 |
|---|---|
| 省略/null/0/false/空串 | 按 schema 区分；合法值保存、回读和正式运行一致 |
| 工具连续同步 | 稳定标识不重复；不自动授予权限、选凭据或发布 |
| 两人并发改授权 | 按约定合并或冲突，无静默丢失更新 |
| 对象归属与角色 | 直接接口请求也受检查，不能只隐藏按钮 |
| 退役/下架/复制 | 遵循既有业务决定，历史与他人副本不误伤 |
| 多文件与同名文件 | ID/归属/会话对应正确，失败项可核对 |
| SSE/长任务 | 流内错误、取消、断连、终态和重复消息得到正确处理 |
| 旧会话/旧数据 | 升级后可读，最终结果与新会话采用兼容规则 |

只选本次相关场景，不要求每次机械执行全部。

## 交付与停止条件

输出：实际完成范围、已通过验证、失败/阻塞/跳过、审查发现、证据位置、剩余风险。
每项验收用 `pass / fail / blocked / not-run / not-applicable` 等明确状态，说明依据。
使用 `check_evidence.py` 检查证据结构、HEAD 与路径等一致性；它不保证语义正确。
缺少依赖、权限或运行实例时，完成可执行部分，再说明具体阻塞与受影响结论。
存在未解决的实质缺陷时，不把该功能整体标为可发布。
已充分覆盖具体风险且必需门禁满足时，停止无目的重测，交付结果。
