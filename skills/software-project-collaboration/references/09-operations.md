# 09 运维、容量与故障处置

目录：运行基线｜可行动监控｜日志与持久化｜容量估算｜故障处置｜恢复演练｜交付与停止条件。

## 运行基线

1. 读取实际部署清单、版本、服务关系、挂载、端口、备份和既有运维规则。
2. 确认当前运行实例与代码/镜像标识；历史对话中的版本只作查找线索。
3. 记录用户已授权的诊断、修复、重启、恢复范围；不重复询问已有授权。
4. 尊重已经暂停的巡检/计划任务，不因本 Skill 自动重新启用。
5. 定时巡检或主动通知需要任务明确授权；一次诊断不自动变成长期自动化。
6. 复用已有日志、指标和状态工具，先解决具体问题，再决定是否增加组件。
7. 为告警和恢复保留负责人、入口和步骤；记录联系人不等于获准向其发送消息。

## 可行动监控

从用户受到的影响定义信号，不先搭一套大平台。

| 类别 | 最小观察 | 可采取的动作 |
|---|---|---|
| 可用与错误 | 关键任务成功/失败、错误类型、失败阶段 | 定位依赖、回退变更或暂停故障入口 |
| 延迟 | API/任务 p50、p95、首字、总耗时 | 区分排队、计算、存储和网络耗时 |
| 需求 | 请求率、文件量、活跃任务、并发与队列 | 限流、排队或调整任务策略 |
| 饱和 | CPU、内存、磁盘、IO、连接池、GPU/KV | 提前处理容量与资源泄漏 |
| 持久化 | 备份年龄、恢复演练、文件关联失败 | 补备份、恢复测试或修复存储链路 |

定义指标分子、分母、时间窗口和取消/重试的计数方式。
HTTP 200 后的流内失败仍计入对应业务失败，不能只统计状态码。
任务成功率不等于业务事实准确率；后者由业务抽检/评测提供。
为阈值记录依据和处理动作；没有基线时先观察，不捏造“行业通用阈值”。
告警应可行动、低噪声并有恢复判断；避免重复告警把同一事件放大。

## 日志与持久化

- 日志关联 request/task/run/conversation 标识、模块、版本、耗时与错误类别。
- 保留定位所需信息，排除密码、token、完整敏感材料和不必要个人信息。
- 生产错误对用户给具体下一步，内部日志保留诊断线索；不要把堆栈暴露到界面。
- 给容器与应用日志都设置大小、数量/时长和总磁盘预算。
- 修改 Docker 默认日志配置后核查既有容器是否实际采用，不能只改配置文件。
- 检查生成文件、上传文件、缓存、临时目录和模型文件各自的保留/清理规则。
- 清理前确认对象归属、引用和恢复需要；不要对未知卷执行笼统 prune。
- 区分运行记录、业务文件和审计记录；删除一种不默认意味着另两种已清除。
- 变更后验证重启仍能找到数据，不能把容器可写层当持久存储。

## 容量估算

### 先定义负载

记录用户数、同时活跃任务、请求率、单任务时长、输入大小、读写比例和峰值持续时间。
区分登录人数、连接数、队列长度、正在执行数；它们不等于同一个“并发”。
选择实际常见、峰值和边界输入做隔离压测，写明数据来源与代表性限制。
使用同版本构建和真实关键依赖；替身压测只能说明替代部分之外的系统能力。

### CPU、内存、磁盘

| 估算 | 用法与限制 |
|---|---|
| 平均在途量约为到达率 × 平均停留时间 | 单位保持一致；用于稳定系统的平均关系，不是峰值保证 |
| 内存约为基线 + worker 增量 + 同时执行任务增量 + 缓存/缓冲 | 各项从测量取值；不能把重复共享内存重复相加 |
| 日志/文件增长约为每日日增 × 保留天数 + 峰值/恢复余量 | 区分压缩、去重、临时文件与备份副本 |
| CPU 需求依据目标吞吐下实测利用率和延迟 | 不盲目线性外推；线程、IO、锁和配额都会改变结果 |

读取容器内存限制、实际用量、OOM 和交换情况，必要时看 PSS 而非简单汇总 RSS。
检查连接池、文件描述符、线程池、队列上限和代理超时是否先于 CPU 成为瓶颈。
以延迟、错误和饱和共同判断容量，不以 CPU/GPU 利用率单项判断“还够用”。
给建议配置附工作负载、测量窗口、余量假设和触发扩容条件。
示例估算必须标示假设，不能变成用户现场实测数据。

### GPU 与模型

- 记录 GPU 型号/可用显存、驱动、运行时、模型权重与量化、KV 类型和服务版本。
- 同时记录输入/输出 token 分布、最大上下文、并发策略、批处理和 prefix cache 条件。
- 模型权重可加载不等于长上下文与目标并发可承受，KV 和工作区占用也需实测。
- 分别测单请求、目标并发、持续负载与长输入；比较首字、总耗时、吞吐和失败。
- 关注排队、抢占、OOM、KV 使用和请求取消后的资源释放。
- 不从“48G 显存”直接承诺“200K 上下文 10 并发”等未经验证的组合。
- NVIDIA、其他加速卡或不同推理后端分别核实兼容性；不要沿用不兼容参数。
- 使用实际版本暴露的指标；vLLM 指标名与含义需对照当前实例核查。

## 故障处置

### 先判断影响和止损

1. 记录首次观察时间、影响范围、用户症状、关键版本和最近变更。
2. 按项目 S0–S3 口径分级；不要把未知根因写成已确定结论。
3. 先检查能快速区分原因的事实：服务就绪、依赖连接、磁盘、资源、队列和错误。
4. 有数据损坏或持续扩大影响迹象时，在既有授权内采取最小可逆止损。
5. 不清空日志、不删除卷、不全量重建环境来“试试看”。
6. 可安全恢复业务时优先恢复，再继续根因分析；记录采取了什么和结果。

### 系统化定位

| 症状 | 首批检查 |
|---|---|
| 首页正常但运行失败 | 正式入口、API 基址、登录权限、上游状态、配置/版本 |
| 任务慢或卡住 | 排队时间、节点耗时、SSE 事件、代理缓冲/超时、模型负载 |
| 重启后文件丢失 | 卷/挂载、权限、会话映射、临时与持久目录、签名 URL |
| 内存持续上升 | 请求生命周期、缓存边界、worker 数量、未释放任务与文件句柄 |
| CPU 空转偏高 | 轮询频率、孤儿任务、重试循环、日志循环、空队列处理 |
| 并发结果异常 | 事务、锁范围、版本冲突、共享状态、重试幂等 |
| 只在客户现场失败 | 架构/运行时、离线依赖、DNS、证书、字体、模型和插件版本 |

每次提出可证伪假设，选择最小检查，再根据证据调整，不同时盲改多个变量。
修复变更应记录任务 BASE/HEAD、实际工作树和被替换产物，复用验证模块。
需要重启时先明确对象、影响、长任务和恢复方式，避免无目标地重启整套服务。
上游故障无法本地修复时，提供准确降级状态；不要用默认成功文案掩盖失败。

## 恢复演练

1. 从授权备份恢复到隔离环境，核查备份内容、校验与版本兼容。
2. 验证数据库、文件、知识库和必要配置之间的引用关系。
3. 核对关键记录数、权限归属、代表性文件和一条用户业务路径。
4. 记录实际恢复耗时、恢复点、缺失数据范围和人工操作步骤。
5. 检查恢复环境不会误发消息、连接生产写入或执行未授权后台任务。
6. 清理隔离演练资源前保留必要证据；只清理本次创建且范围明确的资源。

将 RPO 理解为可接受数据丢失窗口，RTO 理解为恢复服务所需时间目标。
计划目标和演练实测分别记录；没有成功恢复过，不能仅凭备份文件宣称可恢复。
应用回退、数据恢复、故障切换分别写条件，不把它们当同一个动作。

## 交付与停止条件

输出运行现状、证据、影响、根因或待证假设、已做动作、验证结果和剩余问题。
复盘只记录能改变后续行为的结论：触发因素、检测缺口、修复、最小回归和负责人。
更新运维记录与相关 spec/运行清单，避免文档仍指向旧端口、旧卷或旧版本。
诊断受限时说明缺少哪项访问/指标，不猜测现场已健康。
恢复正常且预定观察期达标后停止追加操作，不借故障修复顺带升级无关组件。
需要新的不可逆动作或超出授权范围时，先准备具体方案与证据，再请求必要决定。
