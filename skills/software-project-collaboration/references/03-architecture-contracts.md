## 输入与范围

接收需求目标、验收标准、项目入口、现有代码、目标环境和约束。
沿用项目的需求优先级和风险规则；没有现行规则时用本体系的 MUST/SHOULD/COULD/DEFER 与 R0–R3。
区分“功能重要程度”“改动风险”“故障严重程度”，不得用一个 P0 同时代指三者。
只为本次需求建立需要的合同；已有内容引用路径，不复制第二份。
普通已授权、可逆的设计选择自行推进；涉及未授权的范围、外部副作用或不可逆变更时再确认。

## 先核实现状

1. 读取根入口及更深层规范，确认有效文件、被替代文件和本次适用目录。
2. 记录仓库、分支、HEAD、工作区状态、子模块指针与实际运行版本；各者可能不同。
3. 沿一条真实用户操作，读 UI → API 客户端 → 路由 → 服务 → 数据或上游适配器。
4. 用 `rg` 找调用方、同名配置、重复状态判断和已有公共组件。
5. 读取依赖锁、已安装版本与该版本源码，确认能力已经存在还是仅在开发分支。
6. 核对认证主体、租户、所有者、资源范围、运行身份；API Key 身份不能自动视为真人。
7. 记录现有测试入口、部署方式和证据边界；文档声明不能代替源码或运行结果。

输出一个短现状表，至少包含“事实、来源、对本次方案的影响”。
把无法访问的源码、凭据或环境写为未验证，不据此宣称能力不存在。

## 设计最小完整纵切片

把首个交付单元写成完整用户动作，例如“普通用户保存配置，刷新后仍能读取，失败时知道是否已保存”。
切片必须穿过必要的真实层，包含入口、权限、输入、处理、持久化、反馈及再次访问。
需要历史和文件时，把“离开后找回、预览、下载”算入切片；不要留到最后才发现链路未接。
只搭目录、接口壳、演示页面或大批文档，不能标记为该切片完成。
对 R2/R3 变更，先验证最不确定的一段；给技术探针写问题、预算和退出条件。
把后续可独立交付的能力拆开，避免前后端各做一半却没有一个可使用动作。

按以下顺序选择改造层，前一层足够时停止升级：

| 层级 | 优先做法 | 升级到下一层前说明 |
| --- | --- | --- |
| 1 | 使用现有配置、功能开关和模板 | 缺失的行为是什么 |
| 2 | 复用公共组件、服务或已公开接口 | 接口实际缺哪项能力 |
| 3 | 增加窄适配器、插件或必要挂钩 | 修改面与升级代价 |
| 4 | 对已核对版本做最小 fork 补丁 | 补丁退出条件、上游替代计划 |
| 5 | 新增模块、进程或服务 | 必要隔离、资源需求、运维负责人 |

少容器是成本约束，不是禁止合理隔离；新增容器必须有具体收益和维护代价。
不得为单个消费者先做通用平台、插件市场、事件总线或多级缓存。
对有意保留的简单方案，写当前容量、失效信号和升级路径；不要用“以后再优化”掩盖已知阻塞。

## 确定单一负责方

先填写下表，再决定代码落点。负责方必须是实际路径、模块或接口。

| 对象 | 必须明确的负责方 |
| --- | --- |
| 权限与租户隔离 | 服务端的授权入口；前端只表达可操作性 |
| 配置值与默认值 | 唯一解析位置；适配器不得独立再算一份 |
| 业务状态 | 服务端状态或明确的本地草稿状态 |
| 接口响应信封 | 后端生成者与唯一解包层 |
| 流式事件 | 生产者、版本、消费者、重连恢复来源 |
| 会话及生成文件 | 标识生成、持久化、检索、删除和下载入口 |
| 页面壳与样式变量 | 路由壳、公共组件和设计 token |
| 运行依赖与构建版本 | 锁文件、镜像清单和配置源 |

UI、后端和上游分别负责什么应形成明确边界，不能用同一个“Agent 管理”掩盖三份配置。
复用上游执行器时，先确认定义、授权、选择、执行和审计分别属于谁。
工具发现不自动等于授予使用权；发布、撤权、已发布版本的行为须按产品合同定义。

## 明确接口与状态

接口合同写出方法、路径、认证、请求字段、响应信封、错误语义及兼容范围。
读取真实响应样本，追踪 HTTP 库拦截器与业务封装的返回类型。
若拦截器已返回 body，业务层不得再次按原 HTTP response 解包；对该边界设一个消费者测试。
枚举 `0`、`false`、空字符串、空数组、空对象、`null`、字段缺省各自的业务含义。
更新接口必须说明“缺省=不改”“null=清空”是否成立，不能凭框架默认推断。
错误合同说明用户可见文案、机器可读原因、是否可重试、是否已产生副作用。
分页说明排序稳定键、总数口径、游标或页码，以及并发插入时的预期。
时间说明时区、单位、计时起终点；服务端已有耗时就不让前端另算一个版本。

对长任务、对话和上传，建立生命周期矩阵：

| 状态 | 允许动作 | 持久化及恢复问题 |
| --- | --- | --- |
| 待开始/草稿 | 编辑、提交 | 是否保存草稿，刷新从哪里恢复 |
| 已提交/排队 | 查看、按合同取消 | 重复提交如何识别，排队是否超时 |
| 运行中 | 查看进度、取消 | 断连是否影响任务，最后事件序号是什么 |
| 等待人工输入 | 补充、提交、取消 | 输入是否重复生效，重连如何恢复卡片 |
| 成功/部分成功 | 查看、下载、按合同继续 | 结果和文件是否已持久化 |
| 失败/取消/结果未知 | 重试或查询状态 | 是否有部分成果，重试是否安全 |

事件明确运行 ID、消息 ID、事件 ID 或序号、终态、去重键和历史重放规则。
断开连接、停止显示、任务取消和服务端失败是不同事件；不要共用一个失败布尔值。
缓存只作加速时，说明失效与恢复来源；浏览器存储满不能破坏主链路。

## 处理数据与兼容

标识与显示名分开；改名不得重新生成 ID，删除前检查历史引用。
需要保留历史时，区分登记时快照与当前资源归属；当前授权不能直接照抄历史归属。
多用户更新按现有机制选版本号、ETag、事务或唯一约束；先证明简单机制不足，再引入复杂锁。
跨服务写入说明部分失败和补偿边界；幂等键应绑定同一业务操作，不按每次点击随机重建。
数据库迁移说明旧数据、空库、重复执行、升级顺序和可恢复路径。
区分代码回退、schema 回退、数据恢复；不可逆迁移不得宣称“一键回滚”。
兼容期明确新旧前端、父子仓、上游 API 的可用组合；检查发布次序是否短暂放宽权限。
固定源码和依赖版本；不得用当前上游 HEAD 的能力证明锁定版本可用。
对 CPU、内存、GPU、连接池和队列只给有依据的估算，注明负载假设，容量结论需实测。

## 产物、验证与反例

R0/R1 保留简短设计说明即可；R2/R3 按需要补接口合同、状态表或 ADR，不机械生成全套文档。
产物写“选什么、为什么、改哪里、如何验证、如何恢复”，保留被放弃方案的关键代价。
用真实响应验证合同，用最小页面验证消费者，用必要的真实进程验证集成。
检查成功与应拒绝路径；需要并发、重启或迁移保证时必须覆盖相应场景。
沿全部调用方核对合同变化，检查生成类型、schema、文档和子模块指针是否同步。
不要用接口数、表数、代码行数或测试总数替代用户动作的完成证据。
不要把源码文本断言当作浏览器行为证据，也不要把 mock 集成当作真实上游验收。
不要在实现困难时擅自放宽需求、允许清单、验收标准或权限边界。
完成设计后继续推进已授权实现；只有具体、尚未授权的重大选择才交用户决定。
