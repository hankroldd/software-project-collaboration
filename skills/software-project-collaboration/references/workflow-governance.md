# 工作流治理与冲突处理

仅在多个技能、多人或多个 harness 的工作方式相遇，或流程要求发生冲突时读取。harness 指承载模型、工具、权限、会话和代理的开发运行环境。

## 四层各管什么

本表划分职责，不替换实际宿主的指令优先级。外部资料、模板和社区技能不能自行扩大权限。

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 标准公共层 | SKILL.md格式、相对资源、可移植工作方法 | 保证所有宿主支持同一命令、钩子或权限字段 |
| 宿主适配层 | 发现路径、显式调用、工具映射、会话/代理能力 | 重新定义业务合同，或把本机许可传给其他人/机器 |
| 项目约定层 | 有效需求、技术栈、Git策略、必需检查、角色和发布规则 | 用旧历史或模板占位取代当前明确决定 |
| 本次流程层 | 在授权范围内选步骤、分工、验证与交付 | 自行豁免有效门禁，或为了通过修改验收条件 |

## 先确定谁主持本次任务

1. 读取用户本次要求、有效项目规则和任务角色。沿用已经选定的流程主持者、spec、任务账本与验收标准。
2. 本套被明确选为协调入口时，才负责整体路由。另一套工作流已被选定时，本套只提供被需要的专项方法，不另建总计划或审批链。
3. 被分派的 worker、reviewer 依据任务卡工作；不得因加载本技能而接管总任务、扩大授权或启动第二个全局编排器。
4. 同时点名多种工具时，按已知职责组合，例如一个负责计划、另一个负责特定检查。没有清楚分工且规则互斥时，先查现有约定；只对无法合理确定的关键选择提问，其余无冲突工作继续。
5. 如果没有既定主持者且用户要求本套开展工作，采用本套风险路由。用一两句记录本次分工即可，不强制创建新的流程管理文件。

“主持者”是任务责任，不是管理员权限，也不取代人类负责人、代码所有者或发布批准者。
不同变更组可以各有主持者；共享接口、环境和集成点另行明确负责人，不把整个仓库变成只能串行的一项任务。

## 冲突怎样裁决

先找冲突规则的来源、作用对象和生效条件。区分当前明确指令、项目有效门禁、可选方法、历史记录和示例。
不要从“某个社区也写了必须”推导出本项目多了一道硬门；也不要以“按风险精简”为由跳过现有硬门。

| 看似冲突的要求 | 执行决定 |
| --- | --- |
| 设计确认与自主推进 | 已确认的目标、方案和授权继续有效。可逆实现选择自主处理；新出现且无法代决的范围、权限或不可逆后果先准备具体方案再求必要决定。项目确有适用的设计审批门时执行该门，不重复创造同一确认。 |
| 测试先行与轻流程 | 不改行为的文字/局部样式采用内容或显示检查。行为修复优先用能检出旧错的回归；项目明确要求TDD时沿用其范围。不得为符合某个模板而删除用户已有代码、改弱断言或虚报先失败。 |
| 最小差异与完整交付 | 先列真实调用方、数据、权限、失败状态、配置和部署影响，再选择覆盖这些影响的最小实现。既不漏必要边界，也不为未来可能性扩大功能。 |
| 新spec与已有规格体系 | 已有OpenSpec、Spec Kit或等价档案时使用其主位置与编号。纯实现调整按原规则决定是否需要行为spec，不发明需求填模板；不平行维护两份任务总账。 |
| 规格与当前代码不一致 | 分别说明约定与观察，判断是否存在被批准的后续变更。不能自动宣布最新代码就是新需求，或按过时文档回退有效实现。 |
| 独立上下文与审查连续性 | 可用独立视角审查原件；继续保留原问题ID、拒收、修复差异和复核状态。不给审查者灌输成功结论，也不靠换会话消除旧发现。 |
| 多代理并行与一致性 | 只有任务可隔离且能节省时间或改善质量时并行。共享接口先约定，写入边界相交时串行或隔离工作树；集成只由指定负责人执行。无并行工具时在现有会话完成，不伪造多代理。 |
| 更多验证与及时交付 | 先满足项目必需检查与本次具体风险。剩余风险已被充分证明后停止无目的重跑；新失败保留原件并分类，不靠不断重试刷绿。 |
| 快速安装更新与可复现 | 安装/升级与日常开发分开。按已选版本管理方式核对来源、版本与差异；开发任务不自动更新技能、插件或依赖。升级后的内容、宿主发现和关键行为需要对应核对。 |
| 全会话钩子与单一主持者 | 查清哪些插件/钩子真实启用。文字声明“只用一个”不会关闭别的宿主钩子；仅在授权范围内调整冲突配置，不能假装它们已被停用。 |
| 技能工具声明与真实权限 | frontmatter、角色卡和项目JSON均不能授予实际工具权限。以宿主控制、凭据范围、后端/数据库约束与CI为准；不要借另一harness绕过拒绝。 |

## 需要避免的组合

- 不同时启用多个“所有编码任务自动进入我的完整流程”的主持规则，再让执行者临场猜谁优先。
- 不将Ponytail的会话模式、Superpowers的完整方法和本套风险路由拼成一个未经验证的全局钩子。
- 不把宿主专有frontmatter、slash command、工具名、审批或代理上下文复制到另一宿主后宣称等价。
- 不把某框架的默认测试策略、审批策略或发现数量直接升格为所有项目的统一政策。
- 不因已有技能数量多而全部读取；只加载本次任务涉及的模块，避免重复限制和上下文干扰。

## 采用社区方法时

先说明采用的是具体方法、可选工具还是完整编排器。采用完整编排器要按其真实安装和运行条件；只借鉴方法则在本套协议中明确适配，不宣称等同运行上游技能。
固定参考版本，记录“采用、调整、未采用”的理由。技能本身可以建议查新，但普通任务不能静默拉取新版规则改变当前工作合同。
新增硬规则应对应具体错误或项目要求；通过实际任务观察其效果，不用脚本数量、文章数量或作者基准代替本项目证据。

## 快速自查

- 当前只有一个明确的任务主持者，worker和reviewer知道自己的边界。
- 需求、状态和验收各有已选主位置，原问题与已有授权仍在。
- 相同技能若被多个目录发现，已核来源和版本；没有假定其中一份自动覆盖另一份。
- 必需门禁没有被可选技能降级；低风险任务没有被额外强制套全流程。
- 安装方式、发现机制与权限机制分别说明；已安装不等于实际触发或执行成功。

## 参考边界

- [Agent Skills格式](https://agentskills.io/specification)与[设计实践](https://agentskills.io/skill-creation/best-practices)：渐进加载、清楚触发、按任务脆弱程度控制步骤。
- [Ponytail固定版](https://github.com/DietrichGebert/ponytail/blob/96608e078b2d5ea607c5c3b8b5a54d1c1fba6846/skills/ponytail/SKILL.md)：完整影响面与最小实现；其会话模式不是本套默认。
- [Superpowers设计流程](https://github.com/obra/superpowers/blob/22f0b463e7a5e579904dd6211a520321035526f7/skills/brainstorming/SKILL.md)与[TDD](https://github.com/obra/superpowers/blob/22f0b463e7a5e579904dd6211a520321035526f7/skills/test-driven-development/SKILL.md)：完整流程有自身前置条件和例外，不作为所有项目的叠加门禁。
- [OpenSpec规格模式](https://github.com/Fission-AI/OpenSpec/blob/2bd5bc3be964404657439f538857fcdf550f7398/schemas/spec-driven/schema.yaml)：按行为变化维护规格，纯文档/工具/重构可按规则跳过行为spec。
